# Implementation — 5. Bytecode Compiler

This document describes the design of the bytecode backend: an in-process
**bytecode** (intermediate representation) that flattens each activation's body
and each pattern into a linear instruction sequence, replacing the AST tree-walk
that `RunExpression` and `MatchPattern` perform in the tree-walking interpreter.

The design assumes familiarity with
[3.Analyzer](3.Analyzer.md) (slot assignment, upvalue capture) and
[4.Interpreter and Runtime](4.Interpreter%20and%20Runtime.md) (runtime values,
translation, pattern matching). This document refers to their functions and types
by name.

---

## Goal and scope

The bytecode backend compiles each lambda body and pattern **once** into a flat
instruction stream, so that repeated function calls avoid re-traversing the AST
and re-allocating intermediate nodes. The backend produces **identical observable
behaviour** to the tree-walking interpreter and shares the same runtime.

In scope:

- A flat IR for every *activation body* (the program body, each module binding's
  right-hand side, each lambda-case body) and every *pattern*.
- A compiler from the analyzed AST to that IR.
- A bytecode VM that executes the IR to produce exactly the same graph of
  `RuntimeValue`s the interpreter builds, fed to the **unchanged** reduction
  engine.
- Debug data threaded through the IR so diagnostics still point at source.
- A shared `Runtime` struct so both backends reuse the reduction loop, builtins,
  show, `DeepEqual`, and the stdin machinery.

What the IR does **not** change: it still *builds* the same lazy graph of
`RuntimeValue`s, and the same reducer still forces it. See
[§Design decision](#design-decision-a-builder-vm-not-a-reduction-vm) for why,
and [IMPROVEMENTS.md](IMPROVEMENTS.md) for going further.

---

## What is slow in the tree-walking interpreter

Reduction (`EvaluateToWeakHeadNormalForm`) is already an efficient explicit-stack
loop over `RuntimeValue`s. The repetitive AST work happens in two places, both
run *per activation* / *per β-reduction*:

1. **Body translation — `RunExpression` + `FoldOperation` + `FoldList` +
   `FoldString`.** Every time a closure is applied, the body AST is walked again:
   an interface type-switch per node, `FoldOperation` re-derives the
   application/composition nesting from the operator string, `FoldString`
   re-decodes a string literal into a fresh cons list, and `Name` re-runs its
   `Resolution` switch. For a function called N times this is N re-traversals of
   a fixed tree.

2. **Pattern matching — `MatchPattern`.** Every β-reduction walks the pattern
   AST recursively with an interface type-switch per pattern node.

The bytecode compiles each of these **once** into a linear instruction stream:

- The body's value-graph *shape* is fixed by the source and known at compile
  time. The IR encodes it as a straight-line sequence of "build" instructions
  with pre-resolved slot indices and a pre-decoded constant pool.
- The pattern's structure is encoded as a pre-order instruction sequence with
  pre-resolved bind slots.

---

## Design decision: a *builder* VM, not a reduction VM

There are two ways to "compile to bytecode" a lazy language:

- **(A) A builder VM.** Keep the lazy value graph and the existing reducer. The
  bytecode replaces only the *translation* step (`RunExpression`) and *pattern
  matching*. Executing a body's bytecode constructs the same `RuntimeValue` graph
  the interpreter would, which the unchanged reducer then forces.

- **(B) A reduction VM (a spineless tagless G-machine / CEK machine).** Replace
  the graph-plus-reducer model entirely with instructions that *perform* reduction,
  so that a body never materializes a graph at all.

This design adopts **(A)**. Reasons:

- (A) reuses the entire reduction engine, runtime value set, builtins, `show`,
  `DeepEqual`, thunk memoization, stdin streaming, and the runtime-error/trace
  machinery **unchanged**. That is the maximum-sharing outcome.
- (A) is incremental and low-risk; (B) is a ground-up rewrite of the evaluator.

Because (A) still materializes a fresh value graph per activation, the allocation
count is essentially the same as the interpreter's. (A)'s wins are: no AST
interface dispatch, no `FoldOperation` re-derivation, no `FoldString` re-decode
(string literals become shared constants), no per-`Name` resolution switch or map
lookup, a flat cache-friendly instruction array, and a flat pattern matcher.
The large win — *not building the graph at all* — is what a future (B) machine
buys; see [IMPROVEMENTS.md](IMPROVEMENTS.md).

## Architecture: two front-ends over one shared runtime

Responsibilities split into three pieces:

```
                     ┌─────────────────────────────────────────┐
                     │            Runtime (shared)              │
                     │  • RuntimeValue types (runtime.go)       │
                     │  • EvaluateToWeakHeadNormalForm + helpers │
                     │  • builtins, show, DeepEqual, stdin       │
                     │  • RuntimeError / trace                   │
                     │  • applyClosure  ← mode-specific hook     │
                     └───────────────▲───────────────▲──────────┘
                                     │               │
          ┌──────────────────────────┘               └───────────────────────┐
┌──────────┴───────────┐                                   ┌───────────────────┴────────┐
│   Interpreter (AST)  │                                   │        VM (bytecode)        │
│  • RunExpression     │                                   │  • runBlock / runMatcher    │
│  • MatchPattern (AST)│                                   │  • CompiledProgram          │
│  • Locals / Upvalues │                                   │  • Locals / Upvalues        │
└──────────────────────┘                                   └─────────────────────────────┘
```

- **`Runtime`** owns the reduction loop and everything that does not depend on
  *how a closure's body and pattern are represented*: the `RuntimeValue` types,
  the reducer, `EvaluateToNumber/Tuple/FullNormalForm`, `DeepEqual`, all of
  `show.go`, the builtins, the stdin streams, and error/trace machinery.

- The one place the reducer must do something representation-specific is applying
  a `RuntimeClosure`. `Runtime` calls a hook:

  ```go
  applyClosure func(closure RuntimeClosure, argument RuntimeValue) (RuntimeValue, bool)
  ```

  The interpreter sets it to its AST `ApplyClosure`; the VM sets it to the
  bytecode apply. One indirect call per β-reduction, with a constant target.

- **`RuntimeClosure`** carries both representations; exactly one is populated per
  run (see [§The IR formats](#the-ir-formats)).

- A run is **entirely** interpreted or **entirely** compiled — both front-ends
  set the hook at construction and all closures produced are of one kind.

## The IR formats

Suggested file layout: `ir.go` (types), `compiler.go` (AST → IR), `vm.go`
(`runBlock`, `runMatcher`, bytecode `applyClosure`, compiled driver),
`disasm.go` (human-readable disassembly, debug only).

### Instruction encoding

```go
type Op uint8

type Instr struct {
    Op Op
    A  int32 // primary operand (slot / arity / pool index)
    B  int32 // secondary operand (name index for OpNewThunk; ignored by other ops)
}
```

### `CodeBlock` — one compiled activation body

One per activation: `Program.Body`, each module `Binding.Expression`, each
`LambdaCase.Expression`.

```go
type CodeBlock struct {
    Code    []Instr           // the instruction stream
    Consts  []RuntimeValue    // numbers, prebuilt string lists, builtins, empty tuple, module refs
    Names   []string          // binding names for NewThunk (→ NamedValue.Name, used by traces)
    Pos     []SourcePos       // application spans for OpBuildApp (→ RuntimeApplication.Pos)
    Lambdas []*CompiledLambda // closure templates referenced by OpMakeClosure

    Source Node          // the activation's AST root (debug only)
    Debug  []InstrDebug  // sparse instr-index → source mapping (debug only)
}
```

### Builder opcodes

The complete set, mirroring `RunExpression` + `FoldOperation` + `FoldList`.
(`FoldString` is compiled to a constant.) Stack effect is on a per-block operand
stack of `RuntimeValue`:

| Op | Operand `A` | Stack effect | Meaning |
|----|-------------|--------------|---------|
| `OpConst`       | const idx   | `→ v`            | push `Consts[A]` (number, string-list, builtin, empty tuple, module ref) |
| `OpStdin`       | —           | `→ v`            | push `rt.StdinCodePoints()` |
| `OpBstdin`      | —           | `→ v`            | push `rt.StdinBytes()` |
| `OpLoadLocal`   | slot        | `→ v`            | push `Locals[A]` (a `*NamedValue`) |
| `OpLoadUpvalue` | slot        | `→ v`            | push `Upvalues[A]` |
| `OpBuildCons`   | —           | `h t → cons`     | pop tail, pop head; push `RuntimeCons{head,tail}` |
| `OpBuildTuple`  | arity n     | `e₀…eₙ₋₁ → tup`  | pop n; push `RuntimeTuple` (n ∈ {0,1,3,4,…}; never 2) |
| `OpBuildApp`    | pos idx     | `f a → app`      | pop arg, pop fn; push `RuntimeApplication{fn,arg,Pos[A]}` |
| `OpBuildCompose`| —           | `f g → comp`     | pop g, pop f; push `RuntimeComposition{f,g}` |
| `OpMakeClosure` | lambda idx  | `→ closure`      | build `RuntimeClosure` from `Lambdas[A]` capturing from current frames |
| `OpNewThunk`    | slot, name  | (none)           | `Locals[A] = &NamedValue{Name: Names[B]}` (let pass 1) |
| `OpStoreThunk`  | slot        | `v →`            | pop; `Locals[A].Value = v` (let pass 2) |

### Module references

At compile time the target module's environment does not exist yet. Encode a
module reference as a constant:

```go
type ModuleRef struct {
    Module string // module name; resolved against rt.ModuleEnvironments at run time
    Slot   int
}
```

`OpConst` for a `ModuleRef` is special-cased in `runBlock`: it pushes
`rt.ModuleEnvironments[ref.Module][ref.Slot]` (a `*NamedValue`), preserving
exact parity with the interpreter's module lookup.

### `CompiledLambda` / `CompiledCase` — closures

```go
type CompiledLambda struct {
    Cases           []CompiledCase
    UpvalueCaptures []UpvalueCapture // copied from the analyzer's Lambda.UpvalueCaptures
    Source          *Lambda          // debug: pattern spans for "no pattern matched"
}

type CompiledCase struct {
    Match     []MInstr       // the pattern matcher program (see §Matcher VM)
    MConsts   []RuntimeValue // matcher constants (number/string literals)
    MNames    []string       // bind names (→ NamedValue.Name for pattern bindings)
    Body      *CodeBlock     // the case body
    FrameSize int            // copied from LambdaCase.FrameSize (analyzer)
}
```

`OpMakeClosure A` builds the closure exactly as `MakeClosure` does today, reading
`Lambdas[A].UpvalueCaptures` and the current `Locals`/`Upvalues`.

### `RuntimeClosure` carries both representations

```go
type RuntimeClosure struct {
    Upvalues Environment
    Cases    []*LambdaCase   // interpreter mode (today's field)
    Compiled *CompiledLambda // bytecode mode (nil in interpreter mode)
}
```

The interpreter's `ApplyClosure` reads `Cases`; the VM's apply reads `Compiled`.

### `CompiledProgram` — the top-level unit

```go
type CompiledProgram struct {
    Body    *CodeBlock                 // the program body activation
    Modules map[string][]*CodeBlock    // module name → one CodeBlock per public binding
    Source  *Program                   // debug
}
```

## The builder VM (`runBlock`)

`runBlock` executes a `CodeBlock` against the current `Locals`/`Upvalues` and
returns the single `RuntimeValue` left on the operand stack — the activation's
translated body. It is the bytecode analogue of `RunExpression`, and like it,
**it never forces anything**: it only constructs the lazy graph.

```go
func (vm *VM) runBlock(b *CodeBlock) RuntimeValue {
    stack := vm.opstack[:0] // reusable (non-reentrant; building never forces)
    for pc := 0; pc < len(b.Code); pc++ {
        in := b.Code[pc]
        switch in.Op {
        case OpConst:
            v := b.Consts[in.A]
            if ref, ok := v.(ModuleRef); ok {
                v = vm.ModuleEnvironments[ref.Module][ref.Slot]
            }
            stack = append(stack, v)
        case OpLoadLocal:
            stack = append(stack, vm.Locals[in.A])
        case OpLoadUpvalue:
            stack = append(stack, vm.Upvalues[in.A])
        case OpBuildCons:
            n := len(stack)
            stack[n-2] = RuntimeCons{Head: stack[n-2], Tail: stack[n-1]}
            stack = stack[:n-1]
        case OpBuildApp:
            n := len(stack)
            stack[n-2] = RuntimeApplication{Function: stack[n-2], Argument: stack[n-1], Pos: b.Pos[in.A]}
            stack = stack[:n-1]
        case OpBuildCompose:
            n := len(stack)
            stack[n-2] = RuntimeComposition{Function1: stack[n-2], Function2: stack[n-1]}
            stack = stack[:n-1]
        case OpBuildTuple:
            n := len(stack); k := int(in.A)
            tup := make(RuntimeTuple, k)
            copy(tup, stack[n-k:])
            stack = append(stack[:n-k], tup)
        case OpMakeClosure:
            stack = append(stack, vm.makeClosure(b.Lambdas[in.A]))
        case OpNewThunk:
            vm.Locals[in.A] = &NamedValue{Name: b.Names[in.B]}
        case OpStoreThunk:
            n := len(stack)
            vm.Locals[in.A].Value = stack[n-1]
            stack = stack[:n-1]
        case OpStdin:
            stack = append(stack, vm.StdinCodePoints())
        case OpBstdin:
            stack = append(stack, vm.StdinBytes())
        }
    }
    return stack[len(stack)-1]
}
```

**Operand-stack reuse is safe** because `runBlock` is **non-reentrant**: building
never forces, so it never calls the reducer, and the reducer is the only thing
that triggers another `runBlock` (via `applyClosure`). A single `vm.opstack`
slice suffices.

**`let` lowering.** A `Let` compiles, within the *same* block, to:

```
OpNewThunk s₀ … OpNewThunk sₖ        ; pass 1: every binding's slot exists
<code for RHS₀> OpStoreThunk s₀
…
<code for RHSₖ> OpStoreThunk sₖ       ; pass 2: fill values
<code for the let body>               ; result left on the stack
```

This is a direct linearization of `TreatBindings` — same two-pass order, same
recursion semantics.

## The matcher VM (`runMatcher`)

A pattern compiles to a pre-order instruction sequence operating on a **subject
stack** initialized with the single argument. Each instruction pops one subject;
composite patterns push their children right-to-left (so the leftmost child is
matched first). This is the flat analogue of `MatchPattern`, and it forces
exactly what that function forces — nothing more (the laziness contract is
preserved).

```go
type MInstr struct {
    Op MOp
    A  int32 // slot / arity / const index
    B  int32 // name index (for MOpBind)
}

const (
    MOpNumber MOp = iota // pop; EvaluateToNumber; fail unless == MConsts[A]
    MOpBind              // pop; frame[A] = &NamedValue{Name: MNames[B], Value: subject}
    MOpTuple             // pop; force WHNF; arity A; cons/tuple duality; push children or fail
    MOpString            // pop; walk spine vs MConsts[A] code points; fail on mismatch
)
```

`MOpTuple` reproduces the cons/tuple duality of `MatchPattern`'s `TuplePattern`
case exactly: an arity-2 pattern matches a `RuntimeCons` (head and tail) or a
length-2 `RuntimeTuple`; any other arity requires a `RuntimeTuple` of that
length. `MOpString` reuses the existing spine-walk logic. `ListPattern` never
appears — the analyzer's `NormalizePattern` already rewrites it to nested arity-2
tuple patterns before the compiler runs.

**Pre-order linearization example.** Pattern `[a, [b, c]]`
compiles to:

```
MOpTuple 2          ; pop arg; push inner, a   (a on top)
MOpBind  slot_a     ; pop a
MOpTuple 2          ; pop inner; push c, b     (b on top)
MOpBind  slot_b     ; pop b
MOpBind  slot_c     ; pop c
```

Subject stack empties exactly when the program ends → success.

### The bytecode `applyClosure`

```go
func (vm *VM) applyClosure(closure RuntimeClosure, argument RuntimeValue) (RuntimeValue, bool) {
    cl := closure.Compiled
    for k := range cl.Cases {
        c := &cl.Cases[k]
        frame := make(Environment, c.FrameSize)
        if !vm.runMatcher(c, argument, frame) { continue }
        savedL, savedU := vm.Locals, vm.Upvalues
        vm.Locals, vm.Upvalues = frame, closure.Upvalues
        body := vm.runBlock(c.Body)
        vm.Locals, vm.Upvalues = savedL, savedU
        return body, true
    }
    return nil, false
}
```

The "no pattern matched" error is raised by the reducer (which holds the stack
for the trace), using `closure.Compiled.Source` (the `*Lambda`) for the pattern
span.

## The compiler (AST → IR)

`compiler.go` walks the analyzed AST and emits IR. It runs **after** `Analyze`,
so every `Name.Resolution`/`ResolvedSlot`, every `Lambda.UpvalueCaptures`, and
every `FrameSize` is already filled — the compiler reads them, it does not
recompute scoping.

A `blockBuilder` accumulates one `CodeBlock`'s pools with intern helpers
(`constIndex`, `nameIndex`, `posIndex`, `lambdaIndex`) that deduplicate entries.

### Compiling an expression

`compileExpr(bb, e Expression)` emits code that leaves `e`'s value on the operand
stack:

- `*NumberLiteral` → `OpConst` of an interned `RuntimeNumber`.
- `*StringLiteral` → `OpConst` of the **prebuilt** cons list. `FoldString` runs
  once at compile time and the immutable result is interned as a constant (safe to
  share: it contains no frame thunks and `EvaluateToFullNormalForm` only writes
  back into `RuntimeTuple` slices). This already beats the interpreter, which
  re-folds every time.
- `*Tuple` → 0 elements: `OpConst` of the shared empty tuple. 2 elements:
  `compileExpr` each then `OpBuildCons`. Otherwise: `compileExpr` each then
  `OpBuildTuple n`.
- `*List` → emit nested-cons form (`compileExpr` elements right-to-left, then
  `OpBuildCons` per element ending in the empty-tuple const).
- `*Operation` → transcribe `FoldOperation` directly at compile time; emit
  `OpBuildApp`/`OpBuildCompose` in the same nesting order. The operation's `Pos`
  is computed once and interned.
- `*Let` → `OpNewThunk` for every binding slot, then for each binding
  `compileExpr(RHS); OpStoreThunk slot`, then `compileExpr(body)`.
- `*Name` → by `Resolution`: `ResolveBuiltin`: `stdin`→`OpStdin`,
  `bstdin`→`OpBstdin`, else `OpConst` of the interned builtin value.
  `ResolveModule`: `OpConst` of `ModuleRef{…}`. `ResolveUpvalue`: `OpLoadUpvalue`.
  `ResolveLocal`: `OpLoadLocal`.
- `*QualifiedName` → `OpConst` of `ModuleRef{e.Module, e.ResolvedSlot}`.
- `*Lambda` → `compileLambda` into the block's `Lambdas` pool, then
  `OpMakeClosure idx`.

### Compiling a lambda

`compileLambda(l *Lambda) *CompiledLambda`:
- Copy `l.UpvalueCaptures` and set `Source = l`.
- For each `*LambdaCase`: `compilePattern` → matcher program; `compileExpr` of
  `lcase.Expression` into a fresh `CodeBlock`; copy `lcase.FrameSize`.

### Compiling a pattern (pre-order)

`compilePattern` does a pre-order DFS pushing children right-to-left:
- `*NumberLiteral` → `MOpNumber` (intern into `MConsts`).
- `*Name` → `MOpBind ResolvedSlot` (intern name into `MNames`).
- `*TuplePattern` → `MOpTuple len(SubPatterns)`, then recurse each sub-pattern.
- `*StringLiteral` → `MOpString` (intern code points into `MConsts`).
- `*ListPattern` → unreachable (normalized away); `panic` as a guard.

### Compiling the program

`Compile(analyzer) *CompiledProgram`:
- `Body` = `compileExpr(Program.Body)`.
- For each module, for each public binding in order:
  `compileExpr(binding.Expression)`.
- No reordering; module/binding order matches `Interpreter.Run`.

## Debug data and diagnostics

All error machinery is unchanged — the IR builds the same `RuntimeValue` graph,
so the same positions and names flow into errors:

- **Application failures**: `OpBuildApp` carries `Pos[A]`, exactly as the
  interpreter's `RuntimeApplication.Pos`.
- **Builtin type errors**: the reducer records `builtinPos` before applying a
  builtin — same path, same span.
- **Reduction traces**: `collectTrace` walks update-frame thunks' `Name`s. Those
  names come from `OpNewThunk`'s `Names` pool and matcher `MOpBind`'s `MNames` —
  identical to the interpreter.
- **"No pattern matched"**: uses `closure.Compiled.Source` (the `*Lambda`) for
  the pattern span.

Each `CodeBlock` also keeps a sparse debug table:

```go
type InstrDebug struct {
    Instr int       // index into CodeBlock.Code
    Pos   SourcePos
    Node  Node      // originating AST node (optional)
}
```

And `disasm.go` provides `Disassemble(*CodeBlock) string` for debugging the
compiler and for a future `--dump-ir` flag.

## Refactoring to share the runtime

To make both backends reuse the reducer, builtins, `show`, `DeepEqual`, thunks,
stdin, and error machinery:

1. **Introduce `Runtime`** holding the fields the reducer and builtins use that
   are not front-end-specific:

   ```go
   type Runtime struct {
       ModuleEnvironments map[string]Environment
       stdinReader  *bufio.Reader
       stdinStream  *NamedValue
       bstdinStream *NamedValue
       builtinPos   SourcePos
       builtinStack []StackFrame
       applyClosure func(RuntimeClosure, RuntimeValue) (RuntimeValue, bool)
   }
   ```

2. **Move onto `Runtime`**: `EvaluateToWeakHeadNormalForm`, `EvaluateToNumber`,
   `EvaluateToTuple`, `EvaluateToFullNormalForm`, `DeepEqual`, the stdin methods,
   `builtinError`, `raiseRuntimeError`, and all of `show.go`. Builtins change
   their signature `func(*Interpreter, …)` → `func(*Runtime, …)`.

3. **`Interpreter` keeps** `RunExpression`, `MakeClosure`, `FoldOperation`/
   `FoldList`/`FoldString`, `TreatBindings`, `ApplyClosure`, `MatchPattern`,
   and its `Run`. It embeds `*Runtime` and sets `applyClosure = i.ApplyClosure`.
   Behaviour is identical to today.

4. **`VM`** embeds `*Runtime`, adds `Locals`, `Upvalues`,
   `Program *CompiledProgram`, the reusable `opstack`/`substack`, and `runBlock`,
   `runMatcher`, `makeClosure`, `applyClosure`, `Run`. It sets
   `applyClosure = vm.applyClosure`.

5. **Shared helper**: pull the string-spine match out of `MatchPattern`'s
   `StringLiteral` case into a `Runtime` method `matchStringSpine` reused by
   both backends.

## Driver, startup, and CLI

`VM.Run` mirrors `Interpreter.Run` step for step, swapping `RunExpression` for
`runBlock`:

```go
func (vm *VM) Run() RuntimeValue {
    // 1. create empty module environments
    for name, module := range vm.modules {
        env := make(Environment, len(module.PublicBindings))
        for j, b := range module.PublicBindings { env[j] = &NamedValue{Name: b.Name.Value} }
        vm.ModuleEnvironments[name] = env
    }
    // 2. fill each module binding by running its compiled block
    for name, blocks := range vm.Program.Modules {
        for j, block := range blocks {
            vm.Locals = make(Environment, vm.modules[name].PublicBindings[j].FrameSize)
            vm.ModuleEnvironments[name][j].Value = vm.runBlock(block)
        }
    }
    // 3. run the program body
    vm.Locals = make(Environment, vm.Program.Source.FrameSize)
    return vm.EvaluateToWeakHeadNormalForm(vm.runBlock(vm.Program.Body))
}
```

**CLI mode selection** in `main.go`: a flag such as
`microfun [--mode=interp|compiled] <path>` (default `interp` until the VM is
proven, then flip the default). Optionally `--dump-ir` to disassemble and exit.

## Caveats and invariants

- **Identical graphs ⇒ identical behaviour.** The correctness argument is that
  `runBlock` builds the *same* `RuntimeValue` graph as `RunExpression` and
  `runMatcher` makes the *same* accept/reject decisions as `MatchPattern`. The
  `*Operation` compiler must be a literal transcription of `FoldOperation`, and
  `MOpTuple` a literal transcription of the `TuplePattern` cons/tuple duality.
- **Laziness must not leak.** `runBlock` must never force; `MOpBind` must store
  the subject thunk without forcing.
- **Operand/subject stack reuse depends on non-reentrancy.** If a future change
  ever makes `runBlock` force mid-build (it must not), the shared `opstack`
  becomes unsafe.
- **`RuntimeClosure` dual fields.** Exactly one of `Cases`/`Compiled` is set per
  run; mixing modes is unsupported.
- **`OpNewThunk` ordering.** All `OpNewThunk` of a let group must be emitted
  before any `OpStoreThunk` of that group (two-pass), or mutual recursion breaks.
- **String-literal constant sharing** rests on immutability; `EvaluateToFullNormalForm`
  only writes into non-empty `RuntimeTuple`s, so this holds.

## Validation strategy

Because both backends must produce identical output, validation is **differential**:

1. **Differential run.** For every example and a corpus of small programs
   exercising each language feature, run `--mode=interp` and `--mode=compiled`
   and assert byte-identical stdout/stderr and exit code.
2. **`examples/core_tests.mf`** is a self-checking PASS/FAIL harness over the
   whole standard library — run it in both modes; both must print all PASS.
3. **Error parity.** Programs that raise runtime errors must produce the same
   located diagnostic and the same `while reducing: …` trace in both modes.
4. **Add `_test.go`** harnesses that run the corpus in both modes and diff, so
   equivalence is a regression gate.
5. **Disassembly sanity**: `--dump-ir` on representative programs, eyeballed
   against the expected lowering.
