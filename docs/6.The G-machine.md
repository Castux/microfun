# Implementation — 6. The G-machine

The G-machine (`internal/backend/machine.go`) is the execution engine: a
spineless-tagless push/enter reducer that runs the flat bytecode
([5.Bytecode and Compiler](5.Bytecode%20and%20Compiler.md)) and reduces the
program body to weak head normal form. It produces ordinary runtime `Value`s
(`internal/value/value.go`), so `show`, equality, the stdin streams, and the
error machinery are written once against `Value` and reused directly.

## Runtime values

A `Value` is a small tagged union passed *by value*:

```go
type Value struct {
    Tag Tag
    Num float64
    Ref any
}
```

A number lives inline in `Num` and never allocates — the win that matters, since
numeric programs allocate the most. Every compound value keeps a pointer in `Ref`
(`*Cons`, `*Tuple`, `*Closure`, `*Builtin`, `*Composition`, `*Thunk`, `*Apply`);
a pointer stored in a Go interface does not heap-allocate the way a boxed
`float64` would, so the boxing cost is paid only by genuinely heap-resident
values.

The heap types:

- **`Thunk`** — a deferred computation that memoises. It has three forms,
  distinguished without a tag field: a stdin cell (`Read != nil`), a graph
  indirection for a pattern binding (`Code == NoCode`, forcing reduces the value
  already in `Value`), and a compiled thunk (`Code >= 0`, forcing runs the body at
  `Code`). Compiled thunks capture the enclosing activation (`Locals` +
  `Upvalues`) by reference. Every thunk memoises (call-by-need): the first force
  writes the result back, so it is never recomputed.
- **`Cons`** — a head/tail pair. Thunky draws no distinction between a 2-tuple
  and a list cons cell, so *every* arity-2 tuple is a `Cons`.
- **`Tuple`** — any other arity (0, 1, 3, 4, …); the empty tuple is also the empty
  list and is a shared immutable singleton.
- **`Closure`** — a `Code` PC, the captured `Env`, the `Frame` size, and the
  `NoMatch` source span (for the "no pattern matched" error).
- **`Builtin`** — a primitive as a first-class value: its `PrimOp`, `Arity`, and
  the `Args` gathered so far. Applying it appends an argument; at saturation the
  reducer runs the operation. This single representation is both the saturated and
  the partially-applied form.
- **`Composition`** — an unreduced `First ∘ Second`; applied to `x` it rewrites to
  `First (Second x)`.
- **`Apply`** — a runtime-synthesised application `Fn Arg`. Compiled code never
  builds one (it pushes arguments and enters the head); the only source is
  reducing a composition.

## The reducer

The machine holds a `control Value` in hand and an explicit, heap-allocated
reduction stack of four frame kinds: **argument frames** (a pending argument plus
its source span); **update frames** (a thunk waiting for its weak-head-normal-form
result); **run frames** (a suspended body activation, see below); and **prim-args
frames** (a saturated builtin gathering its forced operands). `reduce` loops:

1. **Force the control.** While it is a thunk, force it: an already-forced thunk
   yields its value; a stdin cell calls `Read`; a compiled thunk pushes an update
   frame and runs its body from `Code`; a graph-indirection thunk
   (a pattern binding) pushes an update frame and continues with its inner value.
   An `Apply` is unwound by pushing its argument and continuing with its function.
2. **Otherwise the control is in WHNF.** With an empty stack it is the result.
   The top frame decides what happens:
   - **update frame** → write the control back into the thunk (memoising) and pop.
   - **run frame** → a body that suspended at a strict point now has the value it
     needed: inject it into the recorded slot and resume the activation (see below).
   - **prim-args frame** → store the operand just forced; force the next, or — once
     all are in WHNF — run the kernel and continue with its result.
   - **argument frame** → *apply* the control:
     - **Closure** → run its cases from `Code` (a β-reduction in tail position): the
       match instructions force the scrutinee, tag-test, and bind into frame slots,
       jumping to the next case on failure; the matched body leaves a new head and
       spine.
     - **Builtin** → append the argument; when saturated, force its operands through
       a prim-args frame and run the operation; else return a new partial `Builtin`.
     - **Composition** → rewrite `(first ∘ second) arg` to `first (second arg)`.
     - **number / tuple / cons** → the located "cannot apply … it is not a function"
       error.

## runCode — suspendable body execution

`runCode` executes a body: a closure case's match instructions (if any), then its
build instructions. Building never forces — a thunk only captures frames, data only
allocates — and it leaves the head on a reusable operand buffer, returning it at
`Enter`. The only instructions that force are `Prim` (a strict builtin's operands)
and the `Match*` instructions (a scrutinee). Rather than force on the Go call stack,
they **suspend**: the activation snapshots itself into a `contState` — its program
counter (pointing at the suspending instruction), frames, a copy of the operand
buffer, and the subject stack — pushes a run frame, and returns the value to force
to the reduce loop. When that value reaches WHNF the run frame injects it into the
recorded slot and re-enters `runCode`, which re-executes the suspending instruction,
now finding the slot already in WHNF.

This is the property that keeps evaluation depth off the Go stack: forcing a value
whose evaluation forces another value, and so on, produces a chain of run frames on
the heap-allocated reduction stack, not a chain of Go stack frames. Exactly one
activation runs on the shared operand buffer at a time — every suspended ancestor
holds its operands safely in its `contState` — so the single buffer stays valid
across forces. The fast path stays cheap: `shallowWHNF` returns a value already in
WHNF (or a chain of forced thunks) without any suspension, so matching or operating
on an already-evaluated value never touches the suspension machinery.

## WHNF — the re-entrant forcing entry point

`WHNF(v)` is what `show`, `DeepEqual`, full-normal-form forcing, and the prim
kernels call to force a value. An already-forced thunk is followed cheaply;
anything that still needs work — an unforced thunk or a pending `Apply` from a
composition — is handed to the full reducer, which pushes the right update frames
and memoises. Because the reducer keeps evaluation depth on its explicit stack, a
single `WHNF` call forces a value of arbitrary depth without recursing in Go. (A
structural builtin that walks a value's *structure* — `show`, `eval`, `equal`,
`hash` — still recurses in Go over that structure, a separate path that is shallow
for the data these programs hash and print.)

## Builtins and prims

Numeric and comparison builtins (`add`, `sub`, …, `eq`, `lt`, …) are `PrimOp`s
(`internal/value/prims.go`). At saturation the reducer forces **every** operand
left-to-right (through the explicit stack, suspending on any that needs reduction)
and then checks they are all numbers — every operand is forced before any
non-number is reported — and runs a `switch` kernel over unboxed `float64`s. The
binary builtins encode their argument order (`sub a b = b - a`, etc.) in the
kernel, as documented in LANGUAGE.md §13.

Structural builtins (`eval`, `peek`, `show`, `write`, `bwrite`, `equal`, `hash`,
`string`, `internal/value/builtins.go`) are about forcing and printing rather than
arithmetic. Their top-level arguments are forced to WHNF the same way — through the
stack — before the kernel runs, so a deep argument *chain* (such as an iterated
`hash`) is reduced on the explicit stack rather than by the kernel's own re-entrant
`WHNF` recursion; the kernel then forces deeper structure itself. `peek`/`show`
render via `internal/value/show.go`; `equal` compares via `DeepEqual` and `eval`
forces to full normal form via `internal/value/equal.go`; `write`/`bwrite` walk a
list and emit bytes. `stdin`/`bstdin` are lazy cons
streams (`internal/value/stdin.go`) backed by a shared reader, produced one
memoised cell at a time.

## Errors and traces

A `RuntimeError` (`internal/source/errors.go`) carries a message, the source span of
the offending expression (when known), and a *reduction trace*. The Go call stack
is useless for a lazy language — a thunk is built in one place and forced in
another — so the trace is instead the names of the binding thunks (let / module /
pattern) on the update-frame stack when the error happened, walked outermost-first;
anonymous intermediate thunks are skipped, leaving a readable skeleton like
`while reducing: a → b → c`.

Error locations come from the bytecode's position pool: an application failure uses
the `PushArg` span; a prim type error uses the builtin's application span; a
non-exhaustive match uses the lambda's whole pattern span (`NoMatch`). Structural
builtins locate and trace their errors through the machine's "current builtin"
span and stack, set when the builtin is entered. The error is recovered at the
run boundary (`RunSafe`), printed, and the process exits 1; any
non-`RuntimeError` panic is a machine bug and keeps its Go stack trace.
