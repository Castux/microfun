# Implementation — 5. Bytecode and Compiler

The compiler (`internal/backend/compile.go`) translates the Core IR
([4.Core IR and Lowering](4.Core%20IR%20and%20Lowering.md)) into a flat bytecode
(`internal/backend/bytecode.go`) that the G-machine
([6.The G-machine](6.The%20G-machine.md)) runs. Because the Core has already made
laziness, scoping, and desugaring explicit, this pass is mechanical and
syntax-directed.

## The flat bytecode

The whole program is **one** `[]Instr` array. Every body — the program body, each
module binding, each lambda case, each thunk — is a contiguous span of that one
array, reached by its start PC. A thunk or closure value therefore holds an
integer PC, not a pointer to a nested block, which gives better instruction-cache
locality and a single uniform notion of "run instructions from PC P".

```go
type PC = int32
type Instr struct { Op Op; A, B int32 }
```

Operands `A`/`B` are small integers — pool indices, slots, arities, jump targets —
never pointers, so `Code` stays dense. The per-program pools are interned:
`Consts` (numbers, prebuilt strings, builtins), `Posns` (source spans for errors),
`Names` (binding names for traces / show), `ModuleNames`, plus the `Closures` and
`Thunks` template tables.

The opcode groups:

- **Build (never force).** `PushConst`, `PushLocal`, `PushUpvalue`, `PushModule`,
  `PushStdin`, `PushBstdin`, `MakeCons`, `MakeTuple n`, `MakeCompose`,
  `MakeClosure tmpl`, `MakeThunk tmpl`, `StoreLet slot,tmpl`. These push values
  onto the operand stack; the head of a body is whatever is on top at `Enter`.
- **Apply / tail (push-enter).** `PushArg posIdx` pops an operand and pushes it as
  an argument frame; `Enter` ends the span, handing the operand on top back to the
  reducer as the body's head.
- **Match (force + test + bind).** `Case` (case entry / retry point), `MatchNumber
  const,failPC`, `MatchTuple arity,failPC`, `Bind slot,nameIdx`, `NoMatch`. These
  run before a case's body; a failed test jumps to the next case's `Case`.
- (`MatchString` exists in the opcode set but lowering desugars string patterns to
  nested cons/number patterns, so the compiler emits `MatchTuple`/`MatchNumber`
  instead.)

There is **no** primitive opcode inside a body. Builtins — arithmetic included —
are ordinary `Builtin` values applied through the spine and saturated by the
reducer, *after* a body's `Enter` has returned. That is what lets a body never
force while it builds, which in turn lets the machine reuse a single operand
buffer safely (see [6.The G-machine](6.The%20G-machine.md)).

## Two compilation procedures

Mirroring the lowerer's demanded/lazy split, codegen has two procedures:

- **`compileBody(e)`** — `e` is a body in tail position. An `App` pushes its
  arguments rightmost-first (so the leftmost ends up on top of the reduction stack
  and is applied first), then continues with the head, which extends the same
  spine. A `Let` emits a `StoreLet` per binding then continues with its body.
  Everything else builds a value. The caller terminates the span with `Enter`.
- **`compileValue(e)`** — leaves exactly one value on the operand stack and never
  touches the reduction stack, so it is safe in any sub-expression position
  (constructor field, composition operand, application argument). It handles
  literals, constructors, names, closures, thunks, and compositions.

Because lowering guarantees an `App` never appears where a single value is
required, `compileValue` never has to deal with an unflattened application.

## Out-of-line bodies

A span must only ever be reached by *entering* its PC, never by falling through
from the code that built the closure or thunk pointing at it. So lambdas and
thunks are not emitted inline at the point they are referenced. Instead:

- `declareThunk` / `declareLambda` register a template (recording its name /
  capture list) and **queue** the body for later compilation, returning the
  template index that `MakeThunk` / `MakeClosure` / `StoreLet` reference.
- After the program body and the module bindings are emitted, `Compile` drains the
  queue; compiling one queued body may queue more (nested lambdas / thunks), so it
  loops until the queue is empty.

A `ClosureTemplate` carries the closure's `Frame` size, its minimal `Capture`
list (each entry says whether the captured variable comes from the enclosing
frame's locals or its upvalues), and the `*Lambda` source (for the "no pattern
matched" span). A `ThunkTemplate` carries only a `Code` PC and a name index —
thunks capture the whole enclosing frame, so they need no capture list.

## Compiling a lambda's cases

A lambda compiles to its cases laid out consecutively. Each case is

```text
Case
<match instructions, each failing to the next case's Case>
<body instructions>
Enter
```

`compilePattern` emits the match instructions and returns the indices of the
instructions whose jump target must be patched to the case's failure PC — the next
case's `Case`, or, for the last case, a `NoMatch` that raises the located
non-exhaustive-match error. `MatchTuple` on success pushes the matched fields so
the sub-patterns consume them left-to-right; `Bind` binds a slot (and carries the
variable's name for traces / show). Matching and the case body share one
instruction set: there is no separate matcher IR or matcher VM.

## Module and program layout

`Compile` emits the program body first (recording its `Entry` PC and
`EntryFrame`), then each module's bindings in a deterministic (sorted) order — the
order is irrelevant to correctness because module environments are built lazily
before the program runs, but determinism keeps the bytecode stable. Each module
binding records its own `Frame` size, since its right-hand side is its own
activation. Module references resolve at run time against the module environments
via `PushModule` (those environments do not exist at compile time) — the one
indirection the flat model retains. The reference is still a direct index, not a
name lookup: `PushModule`'s operands are a module index (`A`, the binding's
position in the `ModuleNames` pool) and a slot (`B`), and the machine builds its
module environments into a `[][]Value` indexed by that same module index, so a
module reference is two slice indexes — `moduleEnvs[A][B]` — with no per-access
hashing of the module name.
