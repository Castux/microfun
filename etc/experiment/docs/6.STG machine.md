# Implementation — 6. STG machine

This document describes the **spineless tagless G-machine** backend
(`--mode=stg`): a third execution path that *reduces* a function body directly
instead of materializing the `RuntimeValue` graph the builder VM
([5.Bytecode compiler](5.Bytecode%20compiler.md)) still builds. It is the
implementation of [IMPROVEMENTS.md §1](IMPROVEMENTS.md).

It assumes familiarity with [4.Interpreter and Runtime](4.Interpreter%20and%20Runtime.md)
(runtime values, the explicit-stack reducer, pattern matching) and
[5.Bytecode compiler](5.Bytecode%20compiler.md) (the builder VM, the matcher IR).
Files: [stgir.go](../stgir.go) (IR), [stgcompiler.go](../stgcompiler.go) (AST → IR),
[stg.go](../stg.go) (the machine).

---

## Goal: eliminate the application spine

The builder VM compiles each body to instructions that **build** a graph of
`RuntimeApplication` / `RuntimeCons` / `RuntimeTuple` / `NamedValue` nodes, which
the shared reducer then forces. The spine of every call — the chain of
`RuntimeApplication` nodes for `f a b c` — is allocated on the heap and then
immediately taken apart again by the reducer. Per IMPROVEMENTS.md §1 this is where
the allocation cost lives.

The key observation is that the existing reducer
(`EvaluateToWeakHeadNormalForm`) **already** does push/enter on an explicit stack:
a `RuntimeApplication` pushes its argument as a frame and descends to the function;
an argument frame applies the function in hand. So the builder VM's spine nodes are
built only to be destructured one step later.

The STG machine fuses the two steps. When a body's value is **demanded**, its
compiled code pushes its argument thunks *directly* onto the reduction stack and
leaves the head function as the value in hand — **no `RuntimeApplication` node is
ever built**. The reducer's existing argument-frame / update-frame machinery then
applies the head exactly as before. The application spine never touches the heap.

What still allocates: a thunk for each *compound* argument sub-expression (atoms —
names, literals, builtins — are passed by reference with zero allocation), and the
data constructors a program explicitly builds (`RuntimeCons`, `RuntimeTuple`,
closures). What no longer allocates: the application spine.

### WHNF values are unchanged

The STG machine still yields ordinary `RuntimeValue`s as weak-head-normal-form
results: `RuntimeNumber`, `RuntimeTuple`, `RuntimeCons`, `RuntimeClosure`,
`RuntimeBuiltin`, `RuntimePartial`, `RuntimeComposition`. This is the single most
important design constraint: it means every builtin, all of `show.go`, `DeepEqual`,
`EvaluateToFullNormalForm`, the stdin streams, and the runtime-error/trace
machinery are **reused unchanged**. The STG changes *how a body is evaluated* (no
spine graph), not the representation of the values it produces.

## Architecture: a third front-end over the shared runtime

The refactor that made room for the STG is small and lives in
[runtime_core.go](../runtime_core.go):

- **A `reduce` hook on `Runtime`.** `EvaluateToWeakHeadNormalForm` is now a thin
  wrapper that calls `rt.reduce(value)`. The interpreter and builder VM set
  `reduce = reduceGraph` (the explicit-stack reducer that forces the materialized
  graph). The STG machine sets `reduce = reduceSTG` (its own loop). Because
  `EvaluateToNumber` / `EvaluateToTuple` / `EvaluateToFullNormalForm`, `DeepEqual`,
  `matchCase`, and all of `show.go` go through `EvaluateToWeakHeadNormalForm`, they
  automatically use the right reducer for the active backend. A whole run is one
  mode, so the indirect call has a constant, perfectly-predicted target.

- **A shared matcher `Runtime.matchCase`.** The flat pattern matcher (the
  `MInstr` / `MOp` IR from [ir.go](../ir.go)) was extracted from the builder VM so
  the STG reuses it verbatim — patterns compile to the same form in both backends.

The interpreter and builder VM are otherwise untouched and remain the differential
oracles (`tests/run.sh` runs all three and requires byte-identical output).

## Thunks carry code, not a graph

A thunk's deferred computation becomes **code + a captured environment** rather
than an unreduced value graph. `NamedValue` (the universal thunk, see
[4.Interpreter and Runtime §Runtime values](4.Interpreter%20and%20Runtime.md#runtime-values))
gains optional fields used only in STG mode:

```go
type NamedValue struct {
    Name   string
    Value  RuntimeValue   // forced result, or (interpreter/VM, and stdin under STG) a graph
    Forced bool
    Code     *STGBlock    // STG: the body to run when forced
    Locals   Environment  // STG: captured activation frame (whole-frame capture)
    Upvalues Environment  // STG: captured upvalues
    Update   bool         // STG: memoize the result (call-by-need) vs re-run (call-by-name)
}
```

Keeping STG thunks as `*NamedValue` (rather than a new type) is deliberate: `show`,
`DeepEqual`, and `EvaluateToFullNormalForm` use `map[*NamedValue]bool` for cycle
detection and read `Name` for display and traces. STG code-thunks slot straight
into all of that. The interpreter and builder VM never set `Code`, so their
behaviour is byte-for-byte unchanged.

### Whole-frame capture

A thunk captures the **entire current activation frame** (`Locals` + `Upvalues`)
*by reference* — not a minimal free-variable set. This is the deliberate
simplicity/space trade-off (see the decision in [STG_PLAN.md](STG_PLAN.md)):

- No per-thunk free-variable analysis and **no slot renumbering** — the thunk's
  code uses exactly the analyzer's slot numbers for the activation it was created
  in, because it shares that activation's frame.
- The cost is retention: a thunk keeps its whole frame alive even if it references
  one slot. Minimal-capture is listed as future work in IMPROVEMENTS.md §1.

*Closures* still use the analyzer's minimal upvalue capture (as in the interpreter
and builder VM); only thunks capture whole frames. This keeps higher-order
standard-library code from retaining frames through every closure.

### Call-by-need vs call-by-name: the `Update` flag

The interpreter (and builder VM) memoize only **named** bindings — `let`, pattern,
and module bindings become `NamedValue`s whose forced value is written back.
Anonymous application and data-field sub-expressions are *raw graph nodes* that are
**re-evaluated** on each force, never shared. This is observable, because
`peek` / `show` / `write` / `bwrite` return their argument: a side-effecting
argument forced twice prints twice.

The STG mirrors this exactly via the `Update` flag on code-thunks:

| Thunk kind | Created by | `Update` | Semantics |
|------------|-----------|----------|-----------|
| `let` binding        | `SOpStoreLet`        | `true`  | call-by-need (memoized) |
| module binding       | `Machine.Run`        | `true`  | call-by-need (memoized) |
| argument / field / pipe | `SOpThunk`        | `false` | call-by-name (re-run on each force) |
| pattern bind, stdin cell | graph-style (`Value` set) | always memoizes | call-by-need |

When the reducer forces a code-thunk it pushes an update frame **only if**
`Update` is set; a call-by-name thunk gets no update frame and so is re-run on
every force, precisely matching the interpreter's treatment of raw application
nodes. (Graph-style thunks — pattern binds and stdin cells, which set `Value` not
`Code` — always memoize, exactly as the interpreter's `NamedValue`s do.)

Sharing of *real* algorithmic work (e.g. `fibonacci` defined with `let`) is
unaffected, because that sharing flows through named bindings, which memoize. A
self-referential structure like `let ones = [1, ones]` shares because the tail is
the *name* `ones` (an atom that references the memoized `let` thunk directly), not
a fresh thunk.

## The IR (`stgir.go`)

The matcher IR (`MInstr` / `MOp`) is shared with the builder VM unchanged; only the
body encoding differs. An `STGBlock` is always the **tail compilation** of one
expression: the program body, a module binding RHS, a lambda-case body, or a thunk
body. It leaves the expression's WHNF head on a per-block operand stack and pushes
the expression's pending arguments onto the reduction stack.

```go
type STGInstr struct {
    Op STGOp
    A, B, C int32 // operand meaning is opcode-specific
}
```

| Op | Operand | Stack effect | Meaning |
|----|---------|--------------|---------|
| `SOpConst`       | const idx     | `→ v`       | push `Consts[A]` (number, string-list, builtin, empty tuple, module ref→resolved) |
| `SOpStdin` / `SOpBstdin` | —     | `→ v`       | push the lazy stdin code-point / byte stream |
| `SOpLocal`       | slot          | `→ v`       | push `Locals[A]` |
| `SOpUpvalue`     | slot          | `→ v`       | push `Upvalues[A]` |
| `SOpThunk`       | block, name   | `→ thunk`   | push a call-by-name code-thunk capturing the current frames |
| `SOpMakeClosure` | lambda idx    | `→ closure` | build a `RuntimeClosure` from `Lambdas[A]` (minimal upvalue capture) |
| `SOpCons`        | —             | `h t → cons`| `RuntimeCons{h, t}` |
| `SOpTuple`       | arity n       | `e₀…eₙ₋₁ → tup` | `RuntimeTuple` of arity n (n ≠ 2) |
| `SOpCompose`     | —             | `f g → comp`| `RuntimeComposition{f, g}` |
| `SOpPushArg`     | pos idx       | `a →`       | push argument frame `{Argument:a, Pos:Pos[A]}` onto the reduction stack |
| `SOpStoreLet`    | slot, block, name | (none)  | `Locals[A] =` a call-by-need code-thunk over `Blocks[B]` |

`ModuleRef` constants are resolved at run time against `rt.ModuleEnvironments`,
special-cased by `SOpConst` exactly as in the builder VM.

No two-pass `let` lowering is needed (unlike the builder VM and the interpreter's
`TreatBindings`): thunks capture the frame by reference and are lazy, so every
binding slot is filled — in source order — before any binding is forced.

## Compilation: two modes per expression (`stgcompiler.go`)

The compiler runs after `Analyze` and reads its annotations; it never recomputes
scoping. It reuses the builder's pattern compiler (`compilePattern` /
`matcherBuilder`) and `foldString`. The body compiler has two mutually-recursive
procedures, distinguished by whether the value is demanded:

### `compileTail(e)` — value is demanded

Emits code that leaves `e`'s WHNF head on the operand stack and pushes its pending
arguments as argument frames.

- literals / empty tuple / constructors (`Tuple`, `List`, `Lambda`) / names →
  build the value; it *is* the head.
- `Operation ""` (juxtaposition) → **flatten the whole spine** (`compileApp`): for
  `f a1 … an`, push `an … a1` (each via `compileArg`) so `a1` ends up on top and is
  applied first, then `compileTail(f)`. If `f` is itself a parenthesized
  application its `compileTail` extends the same spine — no node or thunk for the
  head chain.
- `Operation ">" / "<"` (pipe) → mirror `FoldOperation`'s nested single-argument
  applications (`compilePipe`); the outer application's argument is the fold of the
  remaining operands, carried in a thunk. The full-chain `Pos` is threaded through
  every level so error locations match `FoldOperation` exactly.
- `Operation "*>" / "<*"` (compose) → build a `RuntimeComposition` value
  (`compileCompose`), transcribing the builder's field order.
- `Let` → one `SOpStoreLet` per binding, then `compileTail(body)`.

### `compileArg(e)` — value is an argument or data field (must stay lazy)

Leaves one value on the operand stack without forcing:

- **application / pipe `Operation`, `Let`** → `SOpThunk` over a sub-block compiled
  with `compileTail(e)` (anything that could force or diverge is deferred).
- **everything else** (atoms and pure constructors — literals, names, qualified
  names, tuples, lists, lambdas, compositions) → built directly, since constructing
  them forces nothing. Their compound fields recurse through `compileArg` and so
  stay lazy.

This keeps laziness exactly as strict as the interpreter while avoiding a thunk
layer for pure constructors — matching the builder VM's eager-construction /
lazy-fields behaviour.

## The machine (`stg.go`)

`Machine` embeds `*Runtime` and adds the compiled program and a reusable operand
buffer. Two routines do the work.

### `runCode` — execute one block

`runCode(block, locals, upvalues, stack) (head, newStack)` runs a block's linear
instructions: it builds values on the reusable operand buffer, allocates thunks
(capturing `locals`/`upvalues` by reference), appends argument frames to the
reduction `stack`, and returns the single remaining operand — the head — together
with the grown stack. It is the analogue of the builder VM's `runBlock` (and of
the interpreter's `RunExpression`), differing only in that trailing arguments go
onto the reduction stack rather than into `RuntimeApplication` nodes.

`runCode` **never forces** (building a thunk only captures frames; building data
only allocates), so it never re-enters the reducer. Two `runCode` calls therefore
never overlap, which is what makes the single reusable operand buffer
(`m.opstack`) safe — the same non-reentrancy argument as the builder VM's
`opstack`. `locals`/`upvalues` are passed as parameters, not machine fields, so
forcing a thunk later — with a *different* captured frame — is just another
`runCode` call with that thunk's frames.

### `reduceSTG` — the reduction loop

`reduceSTG` is a variant of `reduceGraph`. The argument/update-frame machinery and
the builtin / partial / composition / cannot-apply / empty-stack-return cases are
**identical**, because they operate on `RuntimeValue` argument frames. Only two
cases differ:

- **Forcing a `*NamedValue`.** If `Forced`, use `Value`. If it is a code-thunk
  (`Code != nil`): push an update frame *iff* `Update` is set, then
  `control, stack = runCode(Code, Locals, Upvalues, stack)` — the body pushes its
  arguments and leaves its head as the new control. Otherwise it is a graph-style
  thunk (a stdin cell): push an update frame and set `control = Value` (the old
  behaviour).
- **Applying a `RuntimeClosure`.** Beta-reduce *inline*: try each case with
  `matchCase` into a fresh frame; on the first match, pop the argument and
  `control, stack = runCode(case.Body, frame, closure.Upvalues, stack)`. The body's
  arguments land on top of the stack, so currying and tail calls fall out of the
  loop with no Go-stack growth. No match across all cases raises the "no pattern
  matched" error (the loop holds the stack for the trace).

`reduceSTG` also retains the `RuntimeApplication` and graph-`*NamedValue` cases
from `reduceGraph` because the **stdin machinery** (`makeInputStream`) still builds
graph thunks (`Value: RuntimeApplication{reader, 0}`); the STG reducer drives them
unchanged, so the stream code needs no STG-specific path.

### Startup

`Machine.Run` mirrors the interpreter and builder VM: create empty module
environments, then turn each module binding's placeholder into a lazy call-by-need
code-thunk over its compiled block (in a fresh frame), then reduce a code-thunk
wrapping the program body. Module bindings are forced on demand exactly like `let`
bindings, so cross-module mutual recursion resolves regardless of load order.

`RunSTG` provides the same `RuntimeError` recovery boundary as `Interpret` and
`RunVM`, so runtime errors are reported and exit identically.

## Correctness and validation

Correctness rests on the same differential argument as the builder VM, applied to
the STG: it must produce byte-identical output to the interpreter oracle.

- **`tests/run.sh`** runs every case under all three modes and asserts each
  backend matches the interpreter's stdout, stderr, and exit code.
- **`examples/core_tests.mf`** (the in-language stdlib self-check) passes wholly in
  `--mode=stg`.
- **Reduction-trace parity** was the sharpest risk: traces collect the `Name`s of
  update-frame thunks on the stack at error time. The STG pushes update frames only
  for memoizing thunks, and argument thunks are anonymous (`Name == ""`), which
  `collectTrace` already skips — so the chain of *named* (let / pattern / module)
  thunks matches the interpreter's. All `tests/cases/errors` cases produce
  byte-identical located diagnostics and `while reducing: …` traces.

### Invariants

- **Identical WHNF values ⇒ identical behaviour.** The STG yields the same
  `RuntimeValue` shapes the interpreter does; the shared runtime does the rest.
- **Laziness must not leak.** `runCode` and `matchCase` never force beyond what the
  interpreter forces; `compileArg` thunks every possibly-forcing expression.
- **Sharing parity.** `let` / pattern / module bindings memoize; argument / field /
  pipe sub-expressions are call-by-name — matching the interpreter, which is
  observable through the output builtins.
- **Operand-buffer reuse depends on `runCode` non-reentrancy.** If a future change
  ever made `runCode` force mid-build (it must not), the buffer would have to
  become per-call.
- **Whole-frame capture can retain memory** — the documented trade-off, not a
  correctness issue.

## Performance

On `bench/run.sh` the STG is the fastest backend on every case, and triggers fewer
GC cycles than the builder VM on allocation-heavy workloads (`sort`, `list-churn`)
— the spine-elimination allocation win on top of a wall-clock speedup. The spine-
and dispatch-heavy cases (`ackermann`, `collatz`) benefit most, since their cost is
dominated by the application spine the STG no longer builds. The remaining
allocation (argument thunks, retained frames) is what the future work in
IMPROVEMENTS.md §1 — minimal capture, strictness, known-strict builtins — would
attack next.
